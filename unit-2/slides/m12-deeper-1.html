Operation counts and memory traffic: the roofline, blocking, and GPU transfers.

Operations per byte

a+b: 1 operation12 bytesXWT at size N: 2N3 operations3×4N2 bytes=N6
  • Idealized traffic at N = 4,096: 683 operations/byte
  • Addition uses each input once; the product reuses it N times
  • Operations per byte select the lower roofline bound
Notes. The opening measured memory bandwidth; the recaps counted work and examined reuse. Arithmetic intensity connects them: the number of operations divided by the bytes read from and written to memory. Array addition performs one addition per 12 bytes. Multiplying two N by N float32 matrices takes about 2 N cubed operations. Reading both inputs once and writing the result once moves 12 N squared bytes, giving N/6 operations per byte: 683 at N = 4,096. This estimate assumes that each input entry is reused N times without being fetched again from main memory.

The roofline of the T4

  • speed ≤ min(peak rate, 300 GB/s × operations per byte)
Notes. The roofline combines the T4's float32 arithmetic limit, 8.1 trillion operations per second, with its memory bandwidth limit, 300 GB/s multiplied by operations per byte. The limits meet at 27 operations per byte. Array addition performs one operation per 12 bytes, so its upper bound is 25 billion additions per second. A layer with K = 4 performs about 2 operations per byte of X and falls in the memory-bound region. The idealized intensity of the size-4,096 product lies in the compute-bound region; the class measured 2.8 trillion operations per second.

Computing the product in blocks

  • The library computes S one block at a time
  • Reuse cached input blocks for many multiplications
  • Reordering preserves O(nKm) and reduces memory traffic
Notes. Matrix multiplication libraries divide the inputs into blocks small enough to fit together in cache. A block from X and a block from W transposed contribute to a block of S. Each input value is reused for several rows or columns of the other block. Blocking keeps the operation count unchanged while reducing repeated reads from main memory.

When copying takes longer than computing

computation                                 copies across the link      GPU compute time
X @ W.T at size 4,096 on the T4                  12.6 milliseconds     48.7 milliseconds
a + b on 16.8 million numbers on the T4          12.6 milliseconds    0.671 milliseconds
  • Matrix product: copying takes less time than multiplication
  • a + b: copying takes far longer than adding
  • Keep data on the GPU across repeated computations
Notes. The copy times are lower bounds calculated from the data sheet. At 16 GB/s each way, transferring the three size-4,096 matrices (201 MB) takes at least 13 milliseconds. The class measured 49 milliseconds for the product itself. Array addition on 16.8 million values transfers the same 201 MB, but its ideal GPU compute time is under a millisecond. The ratio of these bandwidth-based estimates is about twenty to one. Ask the class to compare their Part 2 copy times for a 67 MB matrix.

Try it on the T4

n = 2 ** 26                                       # 67 million numbers in each array
a = torch.rand(n, device="cuda")
b = torch.rand(n, device="cuda")
c = torch.empty(n, device="cuda")
torch.add(a, b, out=c); torch.cuda.synchronize()     # once, not measured
start = time.perf_counter()
for _ in range(20):
    torch.add(a, b, out=c)
torch.cuda.synchronize()
seconds = (time.perf_counter() - start) / 20
print(f"{n / seconds / 1e9:.1f} billion additions a second, {12 * n / seconds / 1e9:.0f} GB/s")
  • Roofline prediction: at most 300 GB/s, or 25 billion additions/second
Notes. Run this demonstration in a Colab session with a T4, with the arrays already in GPU memory. Ask the class to predict the addition rate from the roofline before running it. The build machine has no GPU, so this slide contains the code without a measured result.

What decides the speed

time≈max(operationspeak rate, bytes movedbandwidth)
  • O( ): growth of the operation count
  • Operations per byte: memory-bound or compute-bound
  • Data location: cache, main memory, or GPU memory
Notes. The two terms estimate the time required for arithmetic and for data movement. The larger term gives the roofline estimate. Big O describes how the operation count grows with input size. Data reuse and memory location determine how many bytes must move and the bandwidth available.
