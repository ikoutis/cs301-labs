  • Row order: the rows one after another

Notes. The memory of a computer is one sequence of addresses, one for each byte. The contiguous NumPy array shown here stores its entries in consecutive addresses. Shape and strides describe the layout: the strides say how many bytes to step for one move along each dimension, 32 to go down a row of 4 numbers of 8 bytes, 8 to go right. The transpose: the same line, read another way

X.T has shape (4, 3) and strides (8, 32)   same memory as X: True
in column order, the line is: [ 0.  4.  8.  1.  5.  9.  2.  6. 10.  3.  7. 11.]   strides: (8, 24)
  • X.T: the two strides swapped; no number moves
  • Column order: the columns one after another (np.asfortranarray)
  • Shape and strides describe the view; the data stays in place
Notes. The transpose costs nothing because it copies nothing: it swaps the strides, so one step along a row of X transposed is a step down a column of X. Fortran, MATLAB and R store matrices column after column; NumPy and PyTorch store them row after row unless asked otherwise.

A cache line: 64 bytes

  • The memory hands the cache 64 bytes at a time: 8 numbers
  • A row uses all 8; a column uses 1, then jumps a row ahead
  • Read in order, the next lines are fetched before they are asked for
Notes. This is why the order matters. A row of the matrix uses every number of every line that comes from memory, and the processor, seeing the reading go in order, fetches the following lines ahead. A column uses one number of each line; while the matrix fits in the cache, the rest of the line is still there when the next column needs it, and beyond that it is gone. For a contiguous image array, an image of shape (h, w, 3) keeps the three colours of a pixel side by side.

Sets: where a cache line may go

  • The cache keeps lines: 8 side-by-side numbers, 64 bytes
  • This cache model: set = line number mod number of sets
  • Here: 16 first-column lines compete for 8 slots in 4 sets
Notes. Assume a base address of zero, 64-byte lines, modulo indexing, LRU replacement, an initially empty cache, and no prefetching or other accesses. Read column 0 from row 0 through row 15. The matrix has 16 rows of 16 float64 numbers, 128 bytes a row, so X[r, 0] lies in line 2r. Its set is 2r mod 8: only sets 0, 2, 4 and 6 are used, with two slots each. The lines of rows 0 to 7 have been evicted by the end of column 0. Sequential row reads spread consecutive lines across sets in this model. For a larger example, use the capacities of this laptop's performance core: L1 data is 48 KiB, 12-way, hence 64 sets; L2 is 2 MiB, 16-way, hence 2,048 sets. In the same indexing model, 2,048 numbers per row means a stride of 256 lines. The set is 256r mod 2048, which takes eight values: 0, 256, ..., 1792. For 2,048 rows, that is 256 lines per set competing for 16 slots, 128 slots in total. These are model counts; the actual L2 placement also depends on physical address mapping. A contiguous NumPy array does not establish that mapping.

One number more in each row, and the lines spread

  • Rows of 17 numbers: every 8 rows, the column slips to the next line and the next set
  • L2 model, aligned column 0, 2,048 rows: 2,048 per row reaches 8 sets; 2,049 reaches all 2,048
Notes. Keep the aligned base and other assumptions of the previous slide. With 17 numbers per row, the first-column line is 2r + floor(r/8); its set is that number mod 8. Rows 0 to 7 use the even sets twice each, rows 8 to 15 the odd sets twice each. All 16 lines fit at the end of column 0. This does not make every read of column 1 a hit: rows 7 and 15 cross a line boundary. With LRU replacement, row 7 also evicts the line needed by row 11, so column 1 has three misses. For 2,048 rows of 2,049 numbers, the first-column line is 256r + floor(r/8). Write r = 8q + t, with q from 0 to 255 and t from 0 to 7. Modulo 2,048, the set is 256t + q, which enumerates every set once. That exact count assumes column 0 and a line-aligned base; other offsets need not visit every set exactly once. Padding spreads these accesses across many more sets. Physical address mapping, prefetching, replacement, and other cache levels affect the measured timing; these set counts alone do not predict a speedup.

A transposed operand in a product: a flag, not a copy

product, n = 4,096       PyTorch     NumPy   what the library is handed
X @ W                    0.194 s   0.227 s   both stored by rows
X @ W.T                  0.196 s   0.237 s   W.T by columns: a flag, no copy
X.T @ W                  0.194 s   0.230 s   X.T by columns: a flag
X.T @ W.T                0.196 s   0.229 s   both flagged
X[:, ::2] @ W            0.201 s             no unit stride: copied first
the copy by itself       0.006 s
  • X @ W.T: the library is told op(W) = transpose; it repacks blocks in the cache as it uses them
  • Transpose flags avoid a full copy; compare the four measured times
  • No unit stride, X[:, ::2]: copied first, one extra pass and a new buffer, not a new O(n³)
Notes. The question that the transpose row of Recap 1 leaves open: if W.T is only metadata, who pays when a product consumes it? For contiguous operands, a separate full transpose copy is usually unnecessary. A product goes to the BLAS routine GEMM, whose interface is C = op(A) op(B): each operand comes with a flag, as is or transposed, and a leading dimension. PyTorch and NumPy read the strides of a view and set the flag; these contiguous transposed views can be passed without a full copy. Other layouts and implementations may require one. Inside, GEMM repacks a block of each operand into a small contiguous buffer in the order its kernel wants, while the block sits in the cache, and reuses it for a whole stripe of the result: the against-the-grain reading happens a few kilobytes at a time and disappears under the arithmetic, which is the blocking of the deeper look. So the four layouts cost about the same, and the differences in the table are the library's kernels for each case: on this laptop the both-flagged product was the slowest in PyTorch (MKL) in one run and the fastest in NumPy (OpenBLAS), and the ratios moved between runs; (W @ X).T is the same product written without flags. The one layout that is copied first is a slice with no dimension of unit stride, X[:, ::2]. The copy by itself takes milliseconds; the product with the freshly copied operand paid more than that here, the price of filling a new 134 MB buffer each time, but it is one pass over the operand, not another n cubed. Compare with X + X.T on the previous slide, which has no blocks to hide behind. The same flags exist in cuBLAS on a GPU.

  • The same count, the same code, the same library: the cores it runs on decide the seconds
  • Core placement, thread scheduling, and a shared power budget affect throughput
  • A timing is a sample of a machine state: compare variants side by side, in rounds, by the median
Notes. The red mark says that this slide's numbers belong to one chip. The laptop that builds these slides has two kinds of cores, 8 fast performance cores and 16 slower efficiency cores, and the library's default is 24 threads over all of them. The cell pins the process to each kind in turn. Pinned to either kind alone, the product takes about the same time; with the default, all cores, it takes about twice as long most of the time and the short time now and then, in stretches of a few seconds: work distribution and the shared power budget are possible contributors. These timings alone do not isolate their effects. This comparison illustrates the variation seen between builds: the count, the code and the library are the same in the three rows; the operating system's choice of cores and the chip's power budget decide the seconds. The larger lesson for measuring: a timing is a sample of a machine state, so variants are compared side by side, in rounds, by the median, never as one timing each. Colab uses different virtual machines; compare its measurements without assuming the laptop’s core configuration applies.
